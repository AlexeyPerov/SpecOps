# Component artifact release, retention and revocation

**Reviewed source policy:** 2026-10-10. App 0.3.0, host 0.1.0, Darwin arm64, schema 1. This document authorizes local candidate construction only. Publication, production signing custody and installed execution acceptance remain separate release decisions.

## Candidate production and legal boundaries

Build the host and its pinned SDK assets in CI/development using existing build scripts. `scripts/components/build-prepared.py` splits the exact finite A inventory into independent Node/Claude/Cursor archives; `obtain-pinned.py` fetches exact official native archives, then `prepare-native.py` inventories the complete native package and pinned upstream notices. The latter deliberately normalizes the upstream executable mode on the voice runtime JSON to non-executable mode; no executable script exception is introduced. Shared Node exists in one component, never inside each agent archive. Codex retains its packaged helpers, search, runtime resources and shared libraries; OpenCode contains its native executable and pinned upstream license. Complete upstream/dependency notice and redistribution review remains required. The inventory checker is not legal clearance.

Run `artifacts.py` with an explicit root, finite manifest recipe, output directory, external Ed25519 PEM key and key ID. Every file hash/byte count/mode must match the reviewed inventory; every entry and nonempty notice must exist. Every executable and native library/helper must be explicitly inventoried and target-native. Traversal, normalization collisions, symlinks/hardlinks/special files, unlisted files, unsupported architecture, credential canaries/full private-key PEMs, credential-shaped lexical tokens, development roots and numeric payload overruns fail before candidate publication. Never execute npm/vendor install scripts on the user machine. Inspection is a bounded scanner, not a proof that arbitrary opaque binaries contain no secrets; audit source/license/signing evidence as well.

USTAR paths and permissions are explicit; uid/gid/mtime/owner names are zero/empty, gzip has no filename and mtime zero, level 6. Same finite files and permissions produce identical archives. A candidate signature authenticates bytes; it does not confer Gatekeeper clearance or a right to redistribute. `smoke.py` extracts only finite regular members with matching hashes and runs copied no-account controls using the copied shared Node, isolated homes and system-only PATH. Keep the original bundled resources until C/D/E and H prove the replacement path functional.

## Signing and native trust contract

Release private keys remain outside the checkout with private permissions, preferably protected CI/hardware custody. The current embedded `release-candidate-v1` key is a locally generated engineering candidate, not an approved production signing identity. Its private PEM is preserved in the local Codex private configuration directory under `specops-release-candidate/catalog-v1.pem`; only its public key and signed unavailable catalog are committed. Promote neither this custody nor this candidate key to production without reviewed release approval. Fixture keys use a public RFC test-vector seed and never enter production trust.

The envelope is strict JSON `{payloadHex, signature}`. Lowercase `payloadHex` encodes exact UTF-8 catalog bytes. Sign `SpecOps component catalog v1` followed by one NUL byte and those exact bytes. Catalog schema 1 binds revision, issue/expiry epoch seconds, rows, complete manifests and cumulative revocations. Manifest signing removes the `signature` property and serializes recursively sorted object keys as compact UTF-8 JSON (integer values only, no floating numbers); sign the domain `SpecOps component manifest v1` plus NUL and that serialization. Each manifest independently carries its Ed25519 key ID/signature. Rust strict signature verification rejects unknown/weak keys and noncanonical signatures. Signing uses OpenSSL Ed25519; verification uses the reviewed [strict native implementation](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict).

Catalog lifetime is at most 31 days; an issue time in the future is rejected. New installs/update selections require unexpired metadata. Installed receipts may revalidate expired, previously authenticated compatible retained manifests offline, but cannot authorize a new install through that path. Persist the authenticated revision and exact catalog payload SHA-256 atomically before using it. Reject lower revision and same-revision/different-payload equivocation; never erase the watermark on expiry, failed refresh, cache cleanup, cancellation or embedded fallback. Receipt reconstruction also requires full file rehash and exact manifest/catalog binding. C owns durable write/recovery and must use this verifier; parsing the A manifest or an on-disk receipt never establishes trust.

Production `TrustPolicy` has no constructor accepting keys, origins or environment overrides. Its embedded origin is currently absent: any remotely installable artifact fails closed. Only `cfg(test)` can construct fixture trust and its logical `https://fixtures.invalid/v1/` identity; the test transport may map that exact logical identity to the bounded loopback server. Installed release code cannot use test keys or endpoint overrides.

## Delivery endpoints, headers, request privacy and retention

An approved release build must pin a reviewed HTTPS origin in native code and immutable schema-versioned artifact URLs. The verifier requires the complete URL `<approved-origin>/v1/<id>-<exact-version>-darwin-arm64.tar.gz`; queries, credentials, fragments, alternate schemes, lookalike hosts, traversal and architecture substitution fail. Production endpoint ownership/publication is **unavailable** pending a reviewed hosting decision. All five current embedded rows explicitly say unavailable with no artifact, rather than advertising an unresolvable download. Other targets are unsupported. `release-unavailable.invalid` candidates and `fixtures.invalid` are never production delivery endpoints.

For approved hosting, use immutable content at versioned paths, `Content-Type: application/gzip`, exact `Content-Length`, `Accept-Ranges: bytes`, hash-derived strong ETag and `Cache-Control: public, max-age=31536000, immutable`. Range responses must return matching Content-Range/ETag; refresh catalogs at a separate HTTPS URL with `application/json`, bounded length and short revalidation lifetime. Do not follow redirects to an arbitrary origin. C must validate partial/resumed responses, size and final SHA-256 before extraction. No installer/account token, profile ID, workspace path or history enters requests; only component version/target and ordinary transport metadata reach hosting. Strip response bodies from UI diagnostics. Public hosting access logs receive only ordinary network data; set the retention period in the eventual approved host review.

Retain every artifact referenced by every supported app's exact compatible catalog, including one compatible rollback candidate where native-store revision allows it. Never overwrite a version URL or substitute upstream latest. App compatibility updates require fresh all-helper/copied/signed-installed acceptance and immutable metadata. Deleting supported artifacts requires an explicit release decision; expired catalogs alone do not permit deleting software still supported by offline receipts. Publication is a separately authorized action after reviewer inspection of candidate inventories, complete license obligations, native signing/hardened-runtime/entitlements and Gatekeeper/quarantine assessment. Preserve quarantine; never clear it to obtain a passing result.

## Revocation, rotation and rollback rehearsal

Publish a higher-revision authenticated catalog with cumulative `(component, exact version, target, bounded remediation reason)` revocations. Revocation supersedes install/launch authorization even for a retained row. The native verifier blocks new installs and new launches, including offline receipt lookup after a known revocation. Keep session/history/credential directories intact. C/D/G must show remediation and let existing leased processes finish or ask for explicit stop; never replace/delete a running executable. Only a new compatible authenticated reviewed artifact may resolve the block. An untrusted error/status/body is not revocation metadata.

The local fixture generator signs revision 1 with all five tiny components and revision 2 revoking one native component. Rust rehearsal verifies both, rejects replay, blocks install and installed-manifest launch lookup without mutating private data. This is source authorization evidence, not a live-process/UI rehearsal; that acceptance belongs to C/D/G/H.

Rotate keys by reviewed application release updating embedded public trust and signing identity, with fresh fixture rejection tests. Remote metadata cannot self-authorize a new key. A compromised old key requires an app update removing it and retaining authenticated revocation knowledge. No persisted-data migration, native-store upgrade/downgrade, credential rewrite or silent history reset is part of rotation/rollback. Rollback requires exact app/host/adapter/target/native-store compatibility and no conflicting process leases; never roll back the catalog revision watermark.
