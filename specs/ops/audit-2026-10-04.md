# Аудит задач интеграции агентских runtime

**Дата:** 2026-10-04, 14:15 MSK

**Статус:** аудит текущего кода и предложение нового плана; реализация не изменена.

**Цель:** использовать популярные ИИ-агенты вместе с их нативными harness в SpecOps. Первый приоритет — Codex, включая отдельный аккаунт относительно Codex desktop.

## Вывод

Направление архитектуры правильное: Sessions → Tauri → Agent Host → нативный runtime. Но текущий результат — основа с fake adapter, а не работающая интеграция Codex. Этап 01 нельзя считать полностью принятым по его собственным критериям. Очередь Claude → Codex → OpenCode → Cursor задерживает главный пользовательский результат и должна быть пересмотрена.

Рекомендуемый первый результат: пользователь устанавливает/указывает поддерживаемый Codex, входит во второй ChatGPT-аккаунт из SpecOps, выполняет задачу в реальном workspace, отвечает на approvals, останавливает turn и продолжает тот же native thread после перезапуска. Аккаунт в отдельном Codex desktop при этом сохраняется.

## Подключение второго аккаунта Codex

### Что поддерживает нативный runtime

Официальный [app-server](https://learn.chatgpt.com/docs/app-server) предоставляет browser/device-code login, API-key login, account state, rate limits и thread/turn protocol. Поэтому SpecOps может использовать нативный harness через app-server; отдельный собственный цикл tools поверх Responses API для этой цели не нужен.

Codex хранит config/state под отдельным [CODEX_HOME](https://learn.chatgpt.com/docs/config-file/config-advanced). Credentials могут храниться в файле под этим каталогом либо OS credential store; способ задаётся [cli_auth_credentials_store](https://learn.chatgpt.com/docs/auth).

**Архитектурное предложение:** запускать app-server с отдельным SpecOps-owned home. Это вывод из документированного механизма настройки, а не уже протестированная многопрофильная возможность SpecOps. Для первого результата достаточно одного отдельного профиля внутри SpecOps и сохранённого аккаунта в desktop. Два одновременных профиля внутри SpecOps — следующий acceptance slice.

### Модель профиля

Добавить `connectionProfileId` как first-class поле в session/native binding и routing requests/events. В профиле хранить только ID, runtime ID, имя, не секретное account summary и ссылку на host-owned storage. Нативные credentials не помещать в frontend snapshots и settings.

Пример логической схемы:

```text
Codex desktop → его существующий home/auth → аккаунт A
SpecOps → Agent Host
             → profile B → app-server B → отдельный home/auth → аккаунт B
             → profile C → app-server C → отдельный home/auth → аккаунт C (позже)
```

Требования к AS03-A и общему контракту:

1. Host создаёт каталог профиля в app data, вне проекта. Передаёт `CODEX_HOME` только дочернему process; не меняет глобальное окружение и default home пользователя.
2. Один app-server process на активный профиль может обслуживать несколько threads/workspaces. Два параллельных аккаунта требуют независимых auth contexts; не переключать login общего process между turns.
3. Для первого проверяемого варианта явно выбрать file credential storage: закрытый каталог, ограниченные права файлов, исключение из diagnostics. Для keyring отдельно доказать namespace isolation; одного предположения об отдельном home недостаточно.
4. При запуске контролировать inherited auth/provider environment, чтобы профиль B не использовал чужой API key/token из окружения host. Делать это адресно для auth variables, сохраняя необходимые workspace environment settings.
5. Login completion привязывать к profile ID, login ID и process generation. Не логировать tokens, OAuth URL query и device codes. Auth progress должен приходить независимо от текущего turn.
6. После входа показывать идентификацию фактически выбранного аккаунта: браузер может уже быть авторизован под A. Пользователь выбирает B в браузере; SpecOps проверяет account state, не предполагает успех по открытию URL.
7. Session binding фиксирует профиль. Logout влияет только на профиль; существующая session показывает auth required и не отправляется автоматически под другим аккаунтом. Rate limits тоже принадлежат профилю, не всему runtime.
8. Все ключи маршрутизации учитывают `(runtimeId, connectionProfileId, nativeSessionId)` плюс turn/generation. Native IDs не считать глобально уникальными между профилями.
9. Resume использует тот же profile/home/native thread. Удалённый профиль или отсутствующая native history дают явное состояние, без незаметного создания нового thread.
10. Новый home имеет собственные config, skills/MCP/plugin settings. Пользователь должен понимать этот scope; чтение workspace instructions остаётся обязанностью нативного harness. Не копировать глобальную папку вместе с credentials для переноса настроек.

**Первый ручной acceptance:** desktop остаётся на A → SpecOps входит на B → показывает B → получает реальный ответ и меняет тестовый файл через native tools → получает allow/deny → cancel → app restart → продолжает тот же thread на B → logout B не меняет A. Доступ к моделям и лимиты проверяются для B, а не выводятся из наличия аккаунта A. Device login тестировать только когда он доступен для выбранного аккаунта и pinned runtime.

Нет требования реализовывать автоматическую ротацию аккаунтов при исчерпании лимитов или перенос native thread между аккаунтами.

## Оценка планов и точечные предложения

Сильные стороны: нативная история как источник истины, SDK вне WebView, capabilities вместо общего огромного API, сохранение provider approvals и отказ от миграций. Слабые стороны: формальные Done без завершённой приёмки, длинная обязательная цепочка всех adapter, отсутствие account profile и перенос важных пользовательских условий в конец.

| Где | Предложение |
| --- | --- |
| Roadmap / 03-A prerequisite | Убрать Claude как обязательное условие Codex. Номера каталогов оставить стабильными идентификаторами; очередность задавать зависимостями и приоритетом |
| 01-B/F | Добавить стабилизацию production binding persistence и restart recovery, а не ещё один codec-only round trip |
| 01-C / 03-B | Разделить native transport и replayable event mapper. У SDK/RPC vendor events могут не иметь общей глобальной sequence; host назначает нормализованный cursor, native item/turn IDs хранит отдельно |
| 03-A-01/03 | Явно добавить profile storage, environment isolation, auth notifications, account identity, logout scope и endpoint/process ownership |
| 03-A-02 / 03-D-01 | Генерировать bindings из pinned binary. Проверять executable version и required schema/API surface, не придумывать protocol-version negotiation, которого может не быть. Unknown additive notification → diagnostic; incompatible required shape → error |
| 03-B/C | Внести profile ID в threads, events, catalogs, approvals, limits и history cache. Минимальный resume/history включить до usable preview; полную reconciliation делать следующей итерацией |
| 03-C-01 | Не сжимать model, reasoning effort, collaboration/plan mode, sandbox и approval policy в одно поле mode. Валидировать сочетания через capabilities pinned runtime |
| 03-C/D | Добавить native configuration parity ledger: workspace instructions, skills, MCP, plugins, hooks/subagents только где реально поддержаны. Различать «работает внутри harness», «отображается» и «редактируется из SpecOps» |
| 02-A | API-key/cloud auth оставить минимальным baseline, но не закреплять отсутствие subscription auth как вечное ограничение. Текущая [официальная справка](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) описывает subscription usage SDK и сторонних приложений; перед реализацией отдельно проверить допустимый login flow и условия embedding |
| 04-A/C/D | Сначала зафиксировать parity/deferred ledger: сохранившийся legacy code не означает доступность функции в новом UI. Разделить core cutover и rich extensions; не задерживать Codex ради всего legacy feature set |
| 05-A/C | [Официальный Cursor SDK](https://cursor.com/docs/sdk/typescript) поддерживает local runtime, user/service API keys и browser-assisted auth. Есть требования к Node/native assets и особые условия single-file bundle. Подтвердить approvals/sandbox/history и стоимость integration spike перед реализацией |
| 06-B/C | Убрать зависимость observability и packaging от handoff. Видимость активных writers, предупреждение второго writer, crash recovery и установленный build нужны уже первому Codex preview |
| 06-A/D | Handoff после двух рабочих runtime, pairwise tests только для включённых runtime. Первый релиз не обязан ждать Cursor или всех четырёх adapter |

«Использовать harness» означает сохранить native agent loop, tools, context management, session history и policy enforcement. Заменить это HTTP-вызовом модели недостаточно. При этом интеграция app-server не обещает копию всех функций Codex desktop: UI-specific, voice/browser/cloud и экспериментальные возможности проверяются отдельно.

Первый preview разумно ограничить текущей платформой пользователя, macOS, с явно указанным support scope. Windows/Linux process supervision и packaging проверять перед объявлением их поддержанными. Нельзя считать девелоперский PATH подтверждением качества установленной сборки.

## Предлагаемые новые задачи

- **AS01-S-01:** полный persisted binding и production restart test — P0.
- **AS01-S-02:** bounded supervisor I/O, graceful shutdown и generation-safe process cleanup — P0/P1.
- **AS01-S-03:** host exit settlement, rejected writes и error redaction — P0.
- **AS01-S-04:** framing/backpressure, terminal-exclusivity и fresh-process resume tests — P1.
- **AS03-P-01:** profile schema, host-owned home/credential storage и auth environment boundary — P0 перед login.
- **AS03-P-02:** pinned app-server client и profile-scoped account/login notifications — P0.
- **AS03-P-03:** нейтральный Sessions gate и runtime/profile creation UI — P1.
- **AS03-M-01:** native threads/turns и deterministic event mapping — P1.
- **AS03-M-02:** approvals/questions/cancel и minimum native-history resume — P1.
- **AS03-R-01:** второй-аккаунт acceptance, auth expiry/quota/recovery и profile isolation — P1.
- **AS03-R-02:** native feature/configuration ledger и model/effort/policy controls — P1/P2 по feature.
- **AS06-C-early:** установленный Codex build, host/Node/native assets, diagnostics и safe update contract — P1 до usable preview.

Без data migrations и compatibility codecs. Любое необходимое изменение persisted schema допускает чистый reset с записью в changelog согласно правилам репозитория.
